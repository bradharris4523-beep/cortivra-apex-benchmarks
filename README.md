## 2. Scientific Benchmark Taxonomy & Fairness Rules

To eliminate ambiguity between exact drop-in operator replacements, compressed weight formats, multi-stage kernel fusion, and opt-in linear-complexity operators, every benchmark in [verify_independently.py](./verify_independently.py) is explicitly categorized and gated by scientific evidence class (`EXACTNESS+PERF`, `ALGO_REF_EXACTNESS`, `COMPRESSION+PERF+QUALITY`, `INTEGRATION+PERF+QUALITY`, `TRAINING_QUALITY+MEMORY`, `RESOURCE+EXACTNESS`, `NUMERICAL_PRECISION`):

| Taxonomy Tag | Scientific Category | Computational Objective & Baseline Fairness |
| :--- | :--- | :--- |
| **`[EXACT-KERNEL]`** | **Drop-In Exact Operator Replacement** | Computes the exact same mathematical function as native PyTorch C++ / cuBLAS (`RMSNorm` with non-unit learned weights, `Softmax`, `Extended-Precision FP32->FP64 GEMV`). Verified against 64-bit IEEE `torch.float64` reference outputs using **Cosine Similarity (`Cos = 1.000000`)**, **Maximum Absolute Error (`Max \|d\| <= 1e-5`)**, and **Relative $L_2$ Error (`RelL2`)**. Tested in **Pre-allocated `out=buf` (`2a`, `2.11x` faster)**, **Allocation-Matched `out=None` (`2b`, `1.47x` faster, independently verified `Max\|d\|=1.0e-6`)**, and **Cold-L2 (`128 MiB` cache flushed before every iteration, `3`)** regimes. |
| **`[UNITARY-4BIT]`** | **Unitary Block-Transformed 4-Bit Weight Codec & In-Register GEMV** | Compresses dense weight tensors into 64-element orthogonal block-transformed tiles at **`4.50 bits/weight`** (`32 bytes` packed 4-bit codes + `4 bytes` scale/offset metadata per 64 weights = **`7.111x` vs FP32 / `3.556x` vs FP16**). Benchmarked head-to-head against both **uncompressed `FP16` cuBLAS (`2.86x–2.99x` faster at `M=1`)** and **`bitsandbytes` 4-Bit `NF4` (`Linear4bit`, `1.02x–1.64x` faster at `M=4..256` with `25%` lower Relative $L_2$ error: `0.068` vs `0.092`)**. |
| **`[FUSED-PIPE]`** | **Multi-Stage Pipeline & Persistent Kernel Fusion** | Fuses multi-step PyTorch operator sequences (`100-Stage Affine State Recurrence`, `HDR Bidirectional Frame Warp + Occlusion Blend`, `2D Depthwise Spatial Stencil Conv + Radiative Gate`, `50-Step CUDA-Graph MLP Training`, `8-Shard In-VRAM AllReduce`) into single fused GPU passes. All static baseline setup buffers (`torch.meshgrid` coordinate grids, `AdamW` optimizer state) are pre-allocated outside the timed loop, and Row `7` compares against **both** the 100-step loop (`176.66x`) and PyTorch's single-launch fused `torch.addcmul` kernel (`0.91x`). |
| **`[ALGO-O(N)]`** | **Opt-In Linear-Complexity $O(N)$ Wave Projection** | Replaces quadratic $O(N^2)$ pairwise softmax attention with a linear $O(N)$ associative spectral wave projection (`apex.wave_attention`, live-measured **`0.00 MiB` auxiliary attention matrix**). Verified on distinct `Q, K, V` tensors against an independent **64-bit IEEE `float64` mathematical reference (`Cos = 1.000000`, `Max \|d\| = 5.7e-07`)**. Unmodified frozen pretrained LLMs default to **Exact Softmax (`wave_attention=False`)**, which is benchmarked with a **growing KV cache (`KV = 64 -> 68`)** in **Row `12c` (`4-Layer 14B-Dim (KV=64->68) [4BIT+EXACT]`, `2.86x` faster)**. |

## 6. Transparent Engineering Scope, Thresholds & Known Limitations

1. **Why Raw Linear Matrices Compress `3.56x vs FP16` (`7.11x vs FP32`) While Full Pretrained LLMs Compress `2.58x–3.55x vs FP16`**:
   - Every 64-weight block in an `nn.Linear` layer is compressed to `36 bytes` (`4.50 bits/weight`), which is strictly **`3.556x` smaller than `FP16` (`16 bits/weight`)** and **`7.111x` smaller than `FP32` (`32 bits/weight`)**.
   - In a complete causal language model (`AutoModelForCausalLM`), `apex.boost()` compresses all transformer projection blocks (`q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`) while deliberately keeping the input token embedding table (`embed_tokens`, e.g., `151,936 x 2048` = `0.58 GiB` in `Qwen2.5-Coder-3B`) and final normalization vectors in native `FP16`/`BF16` precision to preserve exact vocabulary lookup fidelity.
   - On a small `3.09B` model where the `151,936`-token vocabulary embedding represents `~10%` of total parameters, total model footprint shrinks by **`2.58x` Steady / `2.59x` Generation-Peak vs `FP16`** (`5.85 GiB -> 2.27 GiB` Steady, `5.89 GiB -> 2.28 GiB` Gen Peak, and `2.85 GiB` transient streaming peak during `apex.boost()`). On larger models (`8.2B`, `14.8B`, `32.8B`, `72.7B`) where transformer linear layers dominate `93%–98%` of total parameters, total model footprint converges toward the asymptotic limit (**`3.12x–3.55x` vs `FP16` / `6.24x–7.09x` vs `FP32`**).
2. **Small-Batch Decode (`M <= 8`), Large-Prompt Prefill (`M > 8`), Head-to-Head vs. `bitsandbytes` `NF4`, & Shared Scratch Buffer Economics**:
   - For `M = 1..8` (`Batch * SeqLen <= 8`, such as autoregressive token decoding and speculative decoding), `ApexLinear` executes the fused 128-bit in-register transform-domain kernel directly on compressed weights with zero temporary weight unpacking (`2.86x–4.40x` faster than `FP16` cuBLAS and `3.44x–3.46x` lower active peak VRAM).
